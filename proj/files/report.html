1. Project Overview and Dataset Protocol

This report documents the full evaluation of Hearth, a prototype system for ambient-sensing anomaly detection in a smart home environment. The evaluation covers three parts: detection quality of the anomaly model, transport-layer performance comparison across three configurations, and correctness of the privacy enforcement mechanisms. All experiments are run on synthetic data using a deterministic seed, so every number in this report can be reproduced by running the evaluation script.

Dataset Protocol

The dataset is fully synthetic. No real person is sensed. The data generator simulates a single-occupant household with six binary ambient sensors: motion in the living room, bedroom, kitchen, and bathroom, plus front door contact and fridge open/close. Each day is represented as a table of 1440 rows (one per minute) and six binary columns. A stochastic baseline routine is generated using probability tables derived from a plausible single-person schedule (sleeping 23:00 to 06:30, morning routine 06:30 to 08:30, daytime activity 08:30 to 18:00, evening 18:00 to 23:00). Random noise is added so no two normal days are identical.

Anomalies are injected on selected days according to a schedule. The five anomaly types used in this evaluation are described in Table 1.

TypeDescriptionExpected tier
inactivityAll sensors zeroed from 11:00 to 16:00 (5 hours). Represents a possible fall or acute illness.URGENT
mild inactivityAll sensors zeroed from 11:00 to 13:30 (2.5 hours). Represents a plausible afternoon rest.NOTIFY
night movementSustained activity in living room, kitchen, and bedroom from 01:00 to 05:00. Represents restless or confused nighttime behavior.URGENT
missed routineKitchen, bathroom, and fridge sensors zeroed during the morning block (06:30 to 08:30). Represents a skipped morning routine.URGENT
benign atypicalActivity pattern consistent with a guest staying over or a sick day in bed. Unusual but not a safety event. Used as the false-positive test case.URGENT (false positive)

Table 1. Anomaly types used in the evaluation, with descriptions and expected escalation tier.

The training set uses 14 normal days (seed 1). The test set uses 12 days (seed 2) with anomalies injected on days 1, 3, 5, 7, and 9 as shown above. Days 0, 2, 4, 6, 8, 10, and 11 are normal. The true-event flag is set to True for all anomaly days except benign atypical, which is the negative case.

The full dataset (20 normal days with anomalies on days 7, 11, 14, and 17) is stored in sensor_dataset.csv. The evaluation uses a separate generated dataset for reproducibility.

Discussion

The RoutineModel detects all four true anomaly days (recall 1.0). The baseline misses both the missed-routine day (day 5) and the mild inactivity day (day 9). This confirms the expected behavior: the baseline only checks whether the total daily activity is outside a fixed band and cannot detect anomalies that change the timing of activity without changing the total amount. The missed-routine anomaly is the clearest example: the resident is active in the afternoon and evening, so total activity is within the normal range, but the morning kitchen and bathroom activity that should occur between 06:30 and 08:30 is absent.

The mild inactivity day (day 9, score 3.23) falls correctly in the NOTIFY tier, demonstrating that the three-tier escalation system works as intended: a shorter, less severe anomaly triggers a softer notification rather than an urgent alert.

The night movement day (day 3) produces the highest routine score by far (77.06). This is expected because nighttime activity is normally near zero, so even a moderate amount of sustained overnight movement produces a very large deviation relative to the learned night-block MAD.

Discussion

The latency values in Table 4 are loopback measurements. In a real deployment, the direct path would have latency determined by the LAN or internet connection. The VPN path would add the encryption overhead plus routing to the VPN exit server. The Tor path would add 50 to 300 milliseconds or more in practice, with high variability.

For the Hearth use case, transport latency has low importance because alert delivery happens at most a few times per day. A resident who falls at 14:00 and whose absence of activity is detected at the end of the daytime block (18:00) would not notice an extra 200 milliseconds of latency when the alert reaches the caregiver. Throughput matters more for the live event stream, but even there the ambient sensor data rate is low (at most a few events per minute in a real deployment).

The important dimension is the threat-model trade-off. The direct path should only be used on a trusted, isolated network segment. The VPN path is acceptable for most deployments but transfers trust to the VPN provider. The Tor path provides the strongest anonymity guarantee but requires the resident or a trusted technician to set up and maintain the Tor daemon, which increases the operational burden significantly.

4. Part C — Privacy Mechanism Experiments

Goal: verify that the four privacy mechanisms (data minimization, consent gate, retention policy, audit log) behave correctly as testable code, not just documentation.

C1. Data Minimization

The home side holds a raw sensor matrix of 6 sensors times 1440 minutes, which is 8,640 binary values per day. The MinimalVerdict object that crosses to the caregiver side has exactly 5 fields: date (ISO date string only), tier (LOG, NOTIFY, or URGENT), block (one of four coarse time-of-day labels), score (a float rounded to one decimal place), and direction (more or less). The reduction ratio is 8640 divided by 5, which is 1,728 to 1. The caregiver cannot reconstruct per-minute activity or room-level counts from these five fields.

Result
Home side: 8,640 raw values per day. Caregiver side: 5 fields per verdict. Reduction ratio: 1,728x. The MinimalVerdict schema is a frozen dataclass; adding new fields to it requires a code change, not just a policy update.

C2. Consent Gate

The resident controls a ConsentGate object. While monitoring is active, verdicts are accepted and delivered normally. When the resident calls pause(), no verdict submitted to the pipeline is accepted or stored, and the caregiver feed returns an empty list regardless of what was previously submitted.

The experiment submits one NOTIFY verdict while monitoring is active, then pauses monitoring and submits one URGENT verdict. The feed is read twice: once after the first submission (active) and once after the pause and second submission.

Result
Feed size while active: 1. URGENT verdict accepted while paused: False. Feed size while paused: 0. The resident's consent overrides alert delivery even for the highest escalation tier.

C3. Retention Policy

The RetentionPolicy class accepts a maximum age in days (default 7). When purge_expired is called with a dictionary of raw data keyed by ISO date and a reference today date, it removes all entries older than the cutoff and returns a report listing the purged dates.

The experiment creates 15 raw day entries (2025-02-01 to 2025-02-15) and calls purge_expired with today set to 2025-02-15 and max_age_days set to 7. The cutoff is therefore 2025-02-08.

Result
Days before purge: 15. Days after purge: 8. Purged dates: 2025-02-01 through 2025-02-07 (7 days). Cutoff: 2025-02-08.

C4. Audit Log

Every call to caregiver_feed() records an access entry in the AuditLog, including the viewer identity, the verdict date, the verdict tier, and the access timestamp. In the main evaluation (Part A), the caregiver feed is read once, which triggers an audit record for each of the 12 verdicts submitted to the pipeline.

Result
Total accesses recorded: 12. Viewer: caregiver_A. All 12 entries are visible in the Audit log tab of the dashboard, including the exact timestamp of each access.

5. Negative and Failure Cases

The project brief requires at least one negative or failure-case experiment. Three are documented in this evaluation.

Negative case 1: Tor transport failure

Failure case — Transport
The Tor path failed with a ProxyConnectionError because no local Tor daemon was running (SOCKS5 proxy at 127.0.0.1:9050 refused the connection). All 300 events were sent but 0 were delivered. Delivery rate: 0%. This is the required documented failure experiment. The failure was handled gracefully; the evaluation script did not crash and recorded the error string in the output.

Negative case 2: False positive on benign atypical day

False positive — Detection
Day 7 (benign atypical, representing a guest visit or sick day in bed) received a RoutineModel score of 37.60 and was escalated to URGENT. This is a false positive: the activity pattern is unusual but does not represent a safety event. The baseline also flagged it as NOTIFY. This is a documented limitation of the prototype: it cannot yet distinguish between "abnormal but safe" and "abnormal and potentially dangerous."

Negative case 3: Consent gate rejects URGENT verdict

Deliberate failure — Privacy mechanism
While the resident has paused monitoring, an URGENT-tier verdict was submitted to the pipeline and was rejected (submit returned False). The caregiver feed was empty. This is an intended negative case demonstrating that the consent gate works correctly even under the strongest escalation tier. The resident's autonomy takes precedence over caregiver notification.

6. Conclusions

The evaluation confirms that all five core requirements from the project brief are satisfied.

The anomaly model detects all four true anomaly types with recall 1.0. The three-tier escalation system correctly places a mild anomaly in NOTIFY and severe anomalies in URGENT. The model outperforms the threshold baseline, which cannot detect missed-routine anomalies or mild inactivity.

The transport comparison documents the performance characteristics and threat-model trade-offs of three configurations and includes the required documented failure case for the Tor path.

All four privacy mechanisms have been verified as correct by running them as code, not just stated in documentation. Data minimization achieves a 1,728x reduction at the home/caregiver boundary. The consent gate correctly blocks delivery when the resident pauses monitoring. The retention policy correctly purges data older than the maximum age. The audit log correctly records all caregiver accesses.

The main limitation of the current prototype is the false positive on the benign atypical day. This represents the fundamental challenge of anomaly detection in ambient smart home environments: any pattern that deviates from the learned normal can look anomalous, even if it has a benign explanation. Addressing this would require either additional context (such as a calendar integration), multi-day pattern modeling, or a caregiver feedback loop that teaches the system over time which anomaly types are genuinely concerning for this specific resident.

All results in this report are fully reproducible by running the evaluation script with the fixed seeds documented in the code.
